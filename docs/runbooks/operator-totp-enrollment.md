# Runbook — Operator TOTP enrollment (Maker-Checker dual control)

**Audience:** operators (back-office admins / super_admins) and whoever performs a deploy.
**Why:** large withdrawals (> `withdrawal_dual_control_usd_threshold`, hard ceiling $20 000) are
**HELD** until a *distinct* operator (the checker) releases them by approving with a valid TOTP
code. After the TOTP migration every operator starts with `totpEnabled = false`, so until
operators enroll, a held large withdrawal **cannot be released and its funds stay blocked**.

This is a **deploy precondition**, not a code bug. Do not rely on dual control in any live
environment until the readiness gate below passes.

---

## The invariant

Releasing a held large withdrawal requires an operator who:

1. passes `requireOperatorMFA` → `role ∈ {admin, super_admin}` **and** `twoFactorEnabled = true`, and
2. passes `totp.verifyForUser` → `totpEnabled = true` with a valid, single-use TOTP code, and
3. is **not** the maker (4-eyes rule — checker ≠ maker).

Therefore dual control is only *usable* when **at least 2 distinct operators are fully MFA
enrolled** (both flags true). Fewer than 2 ⇒ a large withdrawal can be proposed but never released.

## Readiness gate (run before deploy)

```bash
cd backend
npm run check:operator-mfa            # default: requires >= 2 enrolled operators
# stricter posture:
OPERATOR_MFA_MIN_ENROLLED=3 npm run check:operator-mfa
```

- Exit `0` → **READY**: dual control can release large withdrawals.
- Exit `1` → **NOT READY**: lists which operators still need to enroll. Do not deploy dual
  control reliance until this is `0`.
- Exit `2` → error (e.g. DB unreachable).

The script is **read-only** and prints **no secret material** — only per-operator TOTP/2FA status.

## Enrollment flow (self-service — the ONLY secure path)

TOTP secrets are **never** generated by a script or handed out by an admin. Each operator
enrolls their own authenticator app so the shared secret only ever lives on the server row and
the operator's device.

1. Operator logs in and calls **`POST /api/user/me/totp/setup`** (auth required).
   Response: `{ otpauthUri, secret, qr }` — `qr` is a PNG data URL to scan; `secret` is shown
   **once** for manual entry. Never logged, never re-exposed.
2. Operator scans the QR with Google Authenticator / Authy / 1Password, then calls
   **`POST /api/user/me/totp/enable`** with `{ codigo: "<6-digit code>" }`.
   On success `totpEnabled = true` and `twoFactorEnabled = true`.
3. Re-run `npm run check:operator-mfa` until it exits `0`.

To reconfigure a device: **`POST /api/user/me/totp/disable`** with a current code, then repeat.
The legacy `PATCH /me/2fa-toggle` **cannot** turn 2FA off while TOTP is enrolled (that would
strip the login gate) — use `disable` with a code.

## Bootstrapping the first operators

- The very first registered user is created as `super_admin` (see `user.entity.js`).
- Additional operators are promoted via the existing admin role-management path
  (`role → admin | super_admin`).
- You need **at least two** so maker ≠ checker is satisfiable. A single super_admin can never
  self-approve their own proposal (4-eyes is enforced hard in `makerChecker.approve`).

## Failure modes surfaced by the gate

| Symptom | Cause | Fix |
|---|---|---|
| `NOT READY — hay 0` | fresh env, no one enrolled | enroll ≥ 2 operators |
| `NOT READY — hay 1` | only the maker enrolled | enroll a distinct second operator |
| operator shows `TOTP✓ 2FA✗` | inconsistent flags | re-run `enable`, or `disable`+re-enroll |
| operator shows `TOTP✗ 2FA✓` | legacy email-2FA only | enroll TOTP (`setup`+`enable`) |
